# Version 4 — NLP++ Is Debuggable

Version 3 made analyzers **compiled, cloud-built, and installable from npm and pip** (see the
[3.0.0 notes](3.0.0.md)) and turned NLP++ into a first-class language in the editor (the
[3.9.0 notes](3.9.0.md)). Both were about how you **build, deploy and install** an analyzer.

Version 4 is about how you **develop and understand** one: a debugger with breakpoints,
stepping, variables and a call stack inside a running analyzer, and a language server any
LSP-speaking editor can use.

## 🐞 A real debugger, inside a running analyzer

**Live mode runs your analyzer under the engine's own rule debugger and stops between rule
attempts.** It tells you which rule is being tried at which node, whether it matched, and — when
it did not — **how many of its elements matched before it gave up**. That last number is usually
the whole question when a rule does not fire, because it names the element that stopped agreeing
with the text.

- **Breakpoints on rules.** The engine identifies a rule by its head line, so a breakpoint set
  on an element line inside the rule snaps to the head and says so — your eye lands on the line
  that names what you are looking for, which is rarely the head.
- **Breakpoints in `@CODE`, `@POST` and `@DECL`.** Those regions are ordinary imperative code.
  A breakpoint there stops on the line you clicked, *before* it runs, so the variables beside it
  are the ones it is about to act on.
- **Starting takes you somewhere worth looking at.** With breakpoints set, Start runs to them.
  With none, it runs on to the first rule the analyzer tries — not the engine's built-in
  tokenizer, which has no pass file and used to open the session on a blank editor.

## 👣 Stepping

The three step buttons follow where you are:

| | at a rule | in a statement body |
| --- | --- | --- |
| **Step Over** | next rule tried | next statement, calls run whole |
| **Step Into** | next rule matched | next statement, entering a call |
| **Step Out** | next pass | until this function returns |

**Step Into enters a function.** Stopping inside a `@DECL` body lands in the file the function
was *written* in, not the caller's, and its parameters read back as `L()` locals while the
globals it changes update as you step.

Turning on `stopOnRuleFailure` stops on every rule that fails, not only the ones that match.
Most rules fail at most nodes, so this stops very often — it is for tracking down one rule,
not for browsing.

## 🔍 What the panes show

- **Variables** — `L()` locals, `S()` suggested values, `X()` context values and `N()` matched
  elements, with `G()` globals in their own scope. `N()` rows are labelled `N(1)`, `N(2)`: the
  expression you would write, not a description of it. Node attributes — the `("name" value)`
  pairs `.tree` dumps have always printed — appear on the rows that hold them.
- **Nodes in play** — the nodes the rule is actually about, rather than the whole document from
  `_ROOT`. At a match, exactly the nodes the rule took. At an attempt, the current node and the
  candidates after it as `+1`, `+2`, `+3`, as many as the rule has elements. When fewer nodes
  remain than the rule needs, the pane says that, instead of a short list looking like a broken
  one. The whole document is still one row away at the bottom.
- **Current node** — its name, **the text it covers**, its type, its span, and which pass and
  rule line built it. While a rule is being tried, that text is what the rule is being matched
  against.
- **Call Stack** — a frame per call, each named for its function and opening at the line the
  call was *written* on, with the `@CODE`, `@POST` or `@DECL` statement that began it at the
  bottom:

  ```
  inner2()               numbers.nlp:29     <- where execution is
  outer2()               numbers.nlp:33     <- called inner2 from 33
  blockShapes()          numbers.nlp:61     <- called outer2 from 61
  statement at line 87   numbers.nlp:87     <- the @POST that started it
  Pass 2: numbers        numbers.nlp:29
  ```

## ⏪ Replay mode, which steps backwards

A second mode replays the per-pass parse trees the engine already writes to disk. Because the
whole run is already there rather than being generated as you go, **Step Back and
reverse-continue cost nothing** — you can walk a node's history in either direction instead of
re-running the analyzer to get back where you were.

Granularity is the pass, not the rule: between two snapshots the engine ran a whole pass, so
there is no inspecting a partial match. Live mode cannot step backward — a running engine
cannot un-run a rule — so the two are offered side by side rather than one replacing the other.

## 🚀 Getting in without configuring anything

**You do not need a `launch.json`.** Pick a text file in the **Text** view and press
**Debug Analyzer on Current File** on that view's toolbar: the analyzer, the text file, the
engine and the port come from what you have selected. F5 with no configuration does the same.

When you do want a file, three configurations are seeded, named alike for what they do:

- **`NLP++: debug (live)`** — start the analyzer and stop in it. First in the list, so F5 gets it.
- **`NLP++: debug (replay)`** — step the trees of a previous run, forwards or backwards.
- **`NLP++: attach (live)`** — connect to an engine already running under
  `nlp -ANA ... -DEBUG <port>`.

Nothing in the seed needs editing: it uses `${command:nlp.currentAnalyzerDir}` and
`${command:nlp.currentTextFile}`, so it tracks whatever is selected and works unedited on every
analyzer in the folder.

## 🌐 A language server, and a browser build

**Every language feature now runs in a language server** rather than inside the extension:
outline, hover, go-to-definition, find references, rename, completion, signature help, folding,
semantic highlighting, quick fixes, structural diagnostics and formatting. Nothing about them
changed for a VS Code user — the same analysis code gives the same answers — but they no longer
compete with the tree views for the extension host, and **any LSP-speaking editor can now run
them**: point a client at `dist/server.js`.

As of 4.2.0 the same server also builds for a **Web Worker** (`dist/browserServer.js`), for a
web page hosting an NLP++ editor with no server process behind it. A worker has no disk, so the
page sends the analyzer's files and the cross-pass features work over exactly those.

## 📌 About the version number

The extension and the engine are **resynchronised at 4.0.0**. Nothing in this line breaks
compatibility — the engine's protocol additions are additive behind a capability handshake — so
this is a marketing major, not a semver one. Version 4.0.0 itself added no features: it names
what shipped across 3.13 through 3.17, all of it live.

The extension asks the engine what it supports rather than comparing version strings, so against
an older engine a feature is withdrawn *with the reason* instead of sitting there never firing.
Version 4 ships with the engine it needs.
